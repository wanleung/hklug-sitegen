Title: Attackers Abused an Azure API Management Flaw to Reach Stored Customer Secrets, Microsoft Warns
Content:
<p>Microsoft has confirmed that attackers exploited a vulnerability in Azure API Management (APIM) Classic tiers to read stored API credentials belonging to customers. Norwegian authorities have linked the flaw to cyberattacks targeting energy companies. Microsoft is urging customers to rotate any secrets that may have been exposed.</p>
<p>The disclosure, reported by BleepingComputer, places a widely used gateway component at the centre of a credential-theft incident with a confirmed critical-infrastructure connection — elevating it from a routine cloud advisory to a case with evidence of real-world intrusion against high-value targets.</p>
<p>APIM sits in front of internal APIs, third-party services, databases, and Key Vault-backed credentials, concentrating the secrets of everything behind it. A single gateway flaw therefore cascades outward: whoever can read the gateway's stored credentials inherits reach into every system those credentials unlock. Because extracted keys can be replayed directly against origin services, revoking access inside APIM alone may not evict an intruder — treating APIM as plumbing rather than as a credential store inflates the blast radius considerably.</p>
<p>Microsoft's advisory does not publish tenant counts or the breadth of exploitation, and BleepingComputer's reporting does not state whether the energy-sector intrusions relied on anything beyond the stolen credentials. The scope of impact remains, at this stage, directional rather than measured — and the timing of the patch relative to observed exploitation is likewise unstated.</p>
<p>The remediation burden, however, lands entirely on customers — rotation, auditing, and reachability analysis — even when the underlying flaw is provider-side. That asymmetry makes the following checklist the practical priority for administrators running Azure estates.</p>
<h5>What to do</h5>
<p><strong>Rotate every secret at its origin.</strong> Regenerate backend keys, OAuth tokens, and connection strings where they were created — backends, Key Vault, third-party consoles — not merely the copy stored in the gateway. A rotation that only refreshes the gateway copy leaves the original credential live and still compromised.</p>
<p><strong>Inventory APIM instances and identify Classic-tier deployments.</strong> Any Classic-tier instance should be migrated or retired.</p>
<p><strong>Enable diagnostic logging if it is not already on.</strong> Without telemetry, administrators cannot determine whether their secrets were ever touched. Enabling logging is as urgent as rotation; it is the only way to resolve "potentially exposed" into a definite yes or no.</p>
<p><strong>Hunt for unexplained access.</strong> Review Azure Activity logs, APIM diagnostic logs, secret-retrieval operations, anomalous management-plane sign-ins, and unjustified outbound connections. Because the source does not specify when the flaw was patched relative to exploitation, retain and review logs covering as much of the pre-patch window as feasible.</p>
<p><strong>Check for persistence.</strong> Look for newly created keys, unfamiliar service accounts, and outbound integrations that were not present before.</p>
<p><strong>Move toward short-lived credentials.</strong> Prefer managed identities and short-lived tokens over long-lived static keys to reduce the value of any future gateway compromise.</p>
<blockquote>
<p><strong>This week for HK Azure administrators</strong>
Inventory your APIM tiers. Rotate every secret at origin. Turn on diagnostic logging. Then work backwards through Activity logs for the widest window you can retain — without logs, there is nothing to investigate.</p>
</blockquote>
<p>For Hong Kong organisations running hybrid Azure estates, the incident is a general reminder that gateway components are credential stores in all but name, and that detection gaps — not just patch gaps — determine how badly an intrusion unfolds. Without logging, "potentially compromised" can never be narrowed to a definite answer either way.</p>
<p>Administrators should consult Microsoft's MSRC advisory directly for affected versions and patch status, and monitor for updated guidance as the investigation develops.</p>

<hr>
<p>Microsoft 已證實，攻擊者利用 Azure API Management（APIM）Classic 層級的一項漏洞，讀取了屬於客戶的儲存 API 憑證。挪威當局已將該漏洞與針對能源公司的網絡攻擊聯繫起來。Microsoft 正敦促客戶輪換任何可能已外洩的機密憑證。</p>
<p>BleepingComputer 報道的這起披露，將一個廣泛使用的閘道器元件置於一宗憑證盜竊事件的中心，並帶有已確認的關鍵基礎設施關聯——使其超越一般雲端安全公告，成為有證據顯示高價值目標遭真實入侵的案例。</p>
<p>APIM 位於內部 API、第三方服務、資料庫及 Key Vault 支援的憑證之前，集中了其背後一切系統的機密。單一閘道器漏洞因而向外擴散：任何能讀取閘道器儲存憑證的人，就繼承了這些憑證所解鎖的每個系統的存取權。由於提取出的金鑰可直接重放到來源服務，單單在 APIM 內撤銷存取權未必能將入侵者逐出——把 APIM 視為純粹的管道而非憑證儲存庫，會大幅擴大影響範圍。</p>
<p>Microsoft 的公告未公布租戶數量或漏洞被利用的廣度，BleepingComputer 的報道亦未說明能源業入侵是否僅依賴被盜憑證。目前影響範圍仍是方向性而非量化——相對地，修補程式相對於漏洞被利用的時間亦未披露。</p>
<p>然而，補救責任完全落在客戶身上——輪換、審計及可達性分析——即使底層漏洞源自供應商。這種不對稱令以下清單成為 Azure 環境管理員的實際優先事項。</p>
<h5>應採取的行動</h5>
<p><strong>在來源處輪換每項機密。</strong> 在憑證產生的位置重新產生後端金鑰、OAuth token 及 connection string——包括後端、Key Vault、第三方控制台——而不只是閘道器內的副本。只刷新閘道器副本的輪換，會讓原始憑證繼續生效並仍處於受損狀態。</p>
<p><strong>盤點 APIM 實例並識別 Classic 層級部署。</strong> 任何 Classic 層級實例都應遷移或退役。</p>
<p><strong>如尚未啟用，立即啟用診斷日誌。</strong> 沒有 telemetry，管理員無法判斷其機密是否曾被讀取。啟用日誌與輪換同樣緊急；它是唯一能將「可能已外洩」明確化為是或否的途徑。</p>
<p><strong>搜尋無法解釋的存取活動。</strong> 檢視 Azure Activity 日誌、APIM 診斷日誌、機密讀取操作、異常的管理平面登入，以及沒有正當理由的對外連線。由於來源未說明漏洞何時相對於漏洞利用獲修補，請盡可能保留並檢視涵蓋修補前最廣泛時間窗口的日誌。</p>
<p><strong>檢查是否存在持久化機制。</strong> 尋找新建立的金鑰、陌生的服務帳戶，以及原本不存在的對外整合。</p>
<p><strong>逐步改用短效憑證。</strong> 優先使用 managed identities 及短效 token，取代長效靜態金鑰，以降低未來閘道器被入侵時的價值。</p>
<blockquote>
<p><strong>本週給香港 Azure 管理員的要點</strong>
盤點你的 APIM 層級。在來源處輪換每項機密。開啟診斷日誌。然後沿 Activity 日誌回溯你能保留的最寬時間窗口——沒有記錄，便無從調查。</p>
</blockquote>
<p>對香港營運混合 Azure 環境的機構而言，此事件是一次普遍的提醒：閘道器元件在本質上就是憑證儲存庫，而偵測缺口——不只修補缺口——決定了入侵的嚴重程度。沒有日誌，「可能已受損」永遠無法收窄至任何一方的明確答案。</p>
<p>管理員應直接查閱 Microsoft 的 MSRC 公告，以了解受影響版本及修補狀態，並隨著調查進展監察更新指引。</p>
