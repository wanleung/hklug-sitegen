<h3>Fake AUR Packages Impersonating yay and paru Push Malware with Root Privileges, Exposing Arch's Trust-Model Gap</h3>
<p>An attacker uploaded malicious packages to the Arch Linux community repository known as the Arch User Repository (AUR), deliberately impersonating two widely used AUR helper tools: yay and paru. According to BleepingComputer's report, these fake packages do not exploit vulnerabilities in yay or paru themselves. Instead, the attacker took advantage of the AUR's lack of a review mechanism—a trust model that relies on users to verify packages themselves—by uploading lookalike malicious PKGBUILDs that trick victims into running installation scripts with root privileges.</p>
<h4>What Happened</h4>
<p>The AUR is a community-maintained repository where anyone may submit PKGBUILD scripts. Official policy does not vet package contents; verification falls to the end user. This attack targeted that gap directly: the attacker published counterfeit packages with names closely resembling yay and paru. Once installed through a front-end tool, the malicious scripts executed as root. BleepingComputer reports that the offending packages have since been removed from the AUR.</p>
<p>To be clear, the flaw is not in the yay or paru programs themselves—they remain trustworthy AUR helpers. The problem lies in the AUR's permission model, which lets anyone publish packages under the same or a similar name, and in an installation process that routinely executes PKGBUILD build scripts with elevated privileges.</p>
<h4>The Same Pattern as npm and PyPI Typosquatting</h4>
<p>This is not an isolated incident. The npm and PyPI ecosystems have seen repeated typosquatting campaigns in which attackers register names that differ from popular packages by only one or two characters, hoping to catch developers who make a typo or fall victim to dependency confusion. The AUR scenario is structurally identical—only the execution context has changed from <code>npm install</code> to a system-level install requiring root. For Arch users accustomed to <code>makepkg -si</code>, the cost of misplaced trust is correspondingly higher.</p>
<h4>Practical Checklist: Auditing a PKGBUILD</h4>
<p>For system administrators and DevOps engineers still working with the AUR, the following habits are worth adopting:</p>
<ol>
<li><strong>Verify the maintainer's identity</strong>: Check the maintainer's username and contribution history on the AUR web page. Well-known packages typically have maintainers with a long, active track record.</li>
<li><strong>Read the PKGBUILD line by line</strong>: Focus on the <code>build()</code>, <code>package()</code>, and <code>prepare()</code> functions. Look for suspicious <code>curl</code>/<code>wget</code> downloads, <code>eval</code> calls, Base64 decoding, or anything that writes into <code>~/.config</code> or <code>/etc</code>.</li>
<li><strong>Compare against upstream</strong>: Confirm that the <code>source=</code> field points to the official GitHub/GitLab repository or the project's official release page—not a personal fork.</li>
<li><strong>Inspect install scripts</strong>: Pay attention to the <code>post_install</code> hooks in <code>.install</code> files; these are a common hiding place for malicious code.</li>
<li><strong>Track changes with <code>git diff</code></strong>: Both <code>yay</code> and <code>paru</code> support installing from a git clone. Diff the remote update against your local copy before proceeding.</li>
</ol>
<h4>Container Isolation Recommendations</h4>
<p>When installing untrusted or experimental packages, consider the following:</p>
<ul>
<li>Run <code>makepkg</code> inside a <strong>Podman container or systemd-nspawn sandbox</strong> to limit a malicious script's access to the host.</li>
<li>Use a <strong>read-only mounted /usr</strong> on critical systems, and treat the official <code>pacman</code> repositories as the primary software source.</li>
<li>In CI/CD pipelines, treat AUR installs as untrusted code and apply the same level of scanning and approval used for third-party dependencies.</li>
<li>If a root install is unavoidable, run it once in an isolated environment and monitor filesystem and network activity.</li>
</ul>
<h4>Closing Thoughts</h4>
<p>The openness of the AUR is both the strength of the Arch ecosystem and its greatest risk. The fake yay and paru packages are a fresh reminder that, in the Linux world, "community-sourced" does not mean "reviewed." For teams managing multiple Arch or Arch-derived machines, treating AUR packages as a supply-chain risk and instituting a review process is far more practical than cleaning up malware after the fact.</p>

<h3>假冒 yay 與 paru 的 AUR 惡意套件以 root 權限投放惡意軟件，凸顯 Arch 信任模型缺口</h3>
<p>有攻擊者上載惡意套件到 Arch Linux 的社群套件庫 Arch User Repository（AUR），刻意冒充兩款廣受歡迎的 AUR 輔助工具 yay 與 paru。根據 BleepingComputer 的報導，這些假冒套件並非利用 yay 或 paru 本身的漏洞，而是攻擊者利用 AUR 缺乏審核機制的信任模型——即仰賴用戶自行核實套件——上載外觀相似的惡意 PKGBUILD，誘騙受害者在不知情的情況下以 root 權限執行安裝腳本。</p>
<h4>事件經過</h4>
<p>AUR 是由社群維護的套件庫，任何人都可以提交 PKGBUILD 腳本。官方政策不對套件內容進行審核，核實責任落在最終用戶身上。今次攻擊正是針對這個缺口：攻擊者上架了與 yay 及 paru 名稱極為相似的假冒套件。一旦用戶透過前端工具安裝，惡意腳本便會以 root 權限執行。BleepingComputer 報道，相關問題套件已被從 AUR 下架。</p>
<p>需要澄清的是，漏洞並不在 yay 或 paru 程式本身——它們仍是可信的 AUR 輔助工具。問題在於 AUR 的權限模型允許任何人以相同或相近名稱發佈套件，以及安裝過程往往以提升的權限直接執行 PKGBUILD 中的建置腳本。</p>
<h4>與 npm 及 PyPI 仿冒套件如出一轍</h4>
<p>這並非孤立事件。npm 與 PyPI 生態系統近年頻繁出現仿冒套件（typosquatting）攻擊——攻擊者註冊與知名套件僅相差一兩個字符的名稱，伺機捕捉打錯字的開發者或遭受依賴混淆攻擊的受害者。AUR 的情況在結構上完全相同，只是執行環境由 <code>npm install</code> 變成需要 root 權限的系統級安裝。對習慣 <code>makepkg -si</code> 的 Arch 用戶而言，誤信的代價自然更高。</p>
<h4>實務檢查清單：審計 PKGBUILD</h4>
<p>對於仍在使用 AUR 的系統管理員與 DevOps 工程師，建議養成以下習慣：</p>
<ol>
<li><strong>核實維護者身分</strong>：在 AUR 網頁查核套件維護者的使用者名稱與貢獻紀錄，知名套件通常有長期活躍的維護者帳號。</li>
<li><strong>逐行閱讀 PKGBUILD</strong>：重點檢查 <code>build()</code>、<code>package()</code> 及 <code>prepare()</code> 函式，留意可疑的 <code>curl</code>／<code>wget</code> 下載、<code>eval</code> 呼叫、Base64 解碼，以及任何寫入 <code>~/.config</code> 或 <code>/etc</code> 的行為。</li>
<li><strong>比對 upstream</strong>：確認 <code>source=</code> 欄位指向官方 GitHub／GitLab 倉庫或專案官方發佈頁，而非個人帳號的 fork。</li>
<li><strong>檢查安裝腳本</strong>：留意 <code>.install</code> 檔案中的 <code>post_install</code> 鉤子，這是惡意程式碼常見的藏身之處。</li>
<li><strong>使用 <code>git diff</code> 追蹤變更</strong>：<code>yay</code> 與 <code>paru</code> 均支援從 git clone 安裝。安裝前可先比對遠端更新與本地副本的差異。</li>
</ol>
<h4>容器隔離建議</h4>
<p>安裝不可信或實驗性套件時，可考慮以下措施：</p>
<ul>
<li>在 <strong>Podman 容器或 systemd-nspawn 沙箱</strong>內執行 <code>makepkg</code>，限制惡意腳本對主機的存取。</li>
<li>在關鍵系統上使用<strong>唯讀掛載的 /usr</strong>，並以 <code>pacman</code> 官方倉庫作為主要軟件來源。</li>
<li>在 CI/CD 管線中，將 AUR 安裝視為不受信任的程式碼來源，套用與第三方依賴同等級的掃描及審批流程。</li>
<li>若無法避免以 root 安裝，先在隔離環境執行一次，並監控檔案系統及網絡活動。</li>
</ul>
<h4>結語</h4>
<p>AUR 的開放性既是 Arch 生態系統的優勢，也是其最大風險。今次假冒 yay 及 paru 的套件事件再次提醒：在 Linux 世界裡，「來自社群」並不等於「已受審核」。對管理多部 Arch 或衍生發行版機器的團隊而言，將 AUR 套件視為供應鏈風險並建立審核流程，遠比事後清理惡意軟件更為實際。</p>
