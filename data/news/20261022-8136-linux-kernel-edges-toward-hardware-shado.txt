Title: Linux Kernel Edges Toward Hardware Shadow Stacks for Control-Flow Hardening
Content:
<p>Efforts are underway to extend hardware shadow stacks from user space into the Linux kernel, work reported by Phoronix, marking the next stage in a hardening technique that has protected user-space processes from return-oriented programming (ROP) attacks for several years.</p>
<p>Shadow stacks work by keeping a second, hardware-protected copy of function return addresses. When a function returns, the processor compares the address on the normal stack against the copy on the shadow stack, and a mismatch triggers a fault. Because attackers exploiting a buffer overflow or similar memory corruption cannot forge entries on the protected stack, they cannot redirect control flow to gadget chains assembled from existing code — the core mechanic of ROP. Moving that mechanism into kernel space would apply the same guarantee to one of the most security-critical code paths on the system: syscall entry and exit, interrupt handling, and kernel function returns.</p>
<p>For IT professionals planning hardware refreshes, the CPU floor is the most actionable detail. Per Phoronix, the required support exists on Intel CPUs from Tiger Lake onward and AMD processors from Zen 3 onward, which sets a practical floor for where the capability can eventually run. Deployments predating that silicon will not gain the protection regardless of how kernel timelines develop, while organisations running current-generation hardware are already positioned to benefit whenever the capability matures — for them, the remaining wait is on software, not new procurement.</p>
<p>Expectations should be calibrated accordingly: this is patch-development work, not a shipped feature. Kernel-mode operation is also more demanding than user space, because the kernel must tolerate no spurious faults — loadable modules, live-patching mechanisms, and legitimate stack manipulation all have to be reconciled with a fault-on-mismatch model before the feature can be considered safe for production kernels.</p>
<p>Rollout timing will ultimately be governed by enterprise distributions rather than upstream merge dates alone. RHEL, Ubuntu LTS, and SLES users can reasonably expect this to be staged and opt-in across long support cycles, with backporting and hardened defaults following only after the module, live-patching, and stack-manipulation concerns are settled — making it a refresh-planning line item rather than a box that can be ticked today.</p>
<p>The broader context is a long-running hardening push across the Linux stack: user-space shadow stacks were only one piece of a wider control-flow integrity effort that includes fine-grained CFI and stack-protector refinements. Extending hardware enforcement into the kernel would close a gap that exploits have historically targeted, since kernel-mode ROP chains — as used in many privilege-escalation exploits — inherit the same return-address forgery weakness that shadow stacks are designed to eliminate.</p>
<p>Readers should check current patch status against Phoronix's coverage before treating any timeline as firm.</p>
<hr>
<p>據 Phoronix 報導，目前正有工作致力於將硬件 shadow stack 的應用範圍由用戶空間延伸至 Linux kernel，標誌著這項強化技術進入新階段。多年來，該技術一直用於保護用戶空間進程抵禦 return-oriented programming（ROP）攻擊。</p>
<p>Shadow stack 的運作原理是保留一份經硬件保護的函數返回地址副本。當函數返回時，處理器會比較正常 stack 上的地址與 shadow stack 上的副本，若兩者不符便觸發 fault。由於利用 buffer overflow 或類似記憶體損壞漏洞的攻擊者無法在受保護的 stack 上偽造記錄，他們便無法將控制流重定向至由現有代碼組裝而成的 gadget chain——這正是 ROP 的核心機制。將該機制引入 kernel 空間，可把同一保障應用於系統中最關鍵的代碼路徑之一：syscall 進出、中斷處理以及 kernel 函數返回。</p>
<p>對於正規劃硬件更新的 IT 專業人員而言，CPU 的最低型號要求是最實際的關鍵因素。根據 Phoronix，Intel 自 Tiger Lake 起、AMD 自 Zen 3 起的處理器均具備所需支援，這實際上設定了該功能日後可運行的硬件底線。早於此代晶片的部署，無論 kernel 開發時間表如何推進，都不會獲得此項保護；而正在使用最新一代硬件的機構則已具備條件，一旦功能成熟即可受惠——對它們而言，餘下等候的只是軟件進度，而非新的採購安排。</p>
<p>對此應有合理預期：這是 patch 開發階段的工作，並非已推出的功能。Kernel-mode 的運作要求亦比用戶空間更為嚴格，因為 kernel 必須不容許任何虛假 fault——可載入模組（loadable module）、live-patching 機制以及各種正當的 stack 操作，都必須先與「不符即觸發 fault」的模型達成兼容，該功能才可被認為足以用於 production kernel。</p>
<p>推出時程最終將取決於企業級發行版本，而非單靠 upstream merge 日期。RHEL、Ubuntu LTS 及 SLES 用戶可以合理預期，該功能會在長期支持周期內分階段推出並以 opt-in 方式提供；待模組、live-patching 及 stack 操作等問題解決後，才會跟進 backporting 及加固的預設設定——換言之，它是硬件更新規劃中的一項條目，而非今日即可勾選的選項。</p>
<p>更廣闊的背景是 Linux 整個技術堆疊長期以來的強化工作：用戶空間 shadow stack 只是更廣泛的控制流完整性（control-flow integrity）計劃的一部分，該計劃還包括精細粒度的 CFI 及 stack-protector 改進。將硬件強制執行延伸至 kernel，將填補歷來被漏洞利用者針對的缺口——因為 kernel-mode ROP 鏈（眾多權限提升漏洞所採用的手法）同樣繼承了 shadow stack 旨在消除的返回地址偽造弱點。</p>
