Title: Linux 7.4's Rust Drop Is Mostly Housekeeping — and That's the Story
Content:
<p>Miguel Ojeda has sent his Rust pull request for Linux 7.4, and Phoronix reported on 20 October that it is one of the larger drops so far — on the order of 17,000 lines of new and updated Rust kernel code. Crucially, the bulk of that volume comes from refreshing the vendored Zerocopy library and bumping other Rust crates the kernel depends on, not from a single new subsystem landing wholesale.</p>
<p>That distinction matters for anyone counting Rust's footprint in the kernel. Dependency bumps land in bulk during a merge window, while new drivers and subsystem code arrives in small, separately reviewed increments — so a headline line-count for a given cycle usually mixes the two, and the 17,000-line figure is best read as a combined measure of added and modified code rather than a pure addition total. What is clear is the direction: each cycle carries more Rust in the tree than the last, and keeping that code current is itself becoming a significant part of the merge window.</p>
<p>The Zerocopy refresh is the piece that deserves attention beyond the raw numbers. The material available here does not establish which subsystem the vendored library serves — networking, buffer handling, or otherwise — so that scope should be confirmed against the pull request before it is characterised more precisely. What can be said is that Rust-for-Linux increasingly ships with vendored dependencies it maintains itself, which means upstream crate releases and kernel-side updates have to be tracked together. That maintenance loop, rather than any single feature, is the recurring story of recent merge windows.</p>
<p>Also in the 7.4 round-up: work on a <code>cmpxchg</code> emulation function. It sits outside the Rust narrative — ordinary architecture plumbing of the kind that fills most cycles.</p>
<p>Why does this matter beyond mailing lists? For systems programmers, driver authors and infrastructure teams, Rust in the kernel is no longer an experimental sidebar: it is a maintained, growing surface updated on a normal merge-cycle cadence. Organisations carrying their own kernel patches or out-of-tree modules now have a practical incentive to follow Rust-for-Linux's release rhythm.</p>

<hr>
<p>Miguel Ojeda 已向 Linux 7.4 提交其 Rust pull request，Phoronix 於 10 月 20 日報道稱，這是迄今規模較大的一次更新之一 — 涉及約 17,000 行新增及更新的 Rust kernel 代碼。關鍵在於，當中大部分篇幅來自更新內嵌（vendored）的 Zerocopy 函式庫，以及升級 kernel 所依賴的其他 Rust crates，而非某個全新 subsystem 一次性整體納入。</p>
<p>對於任何統計 Rust 在 kernel 中佔比的人來說，這一區別至關重要。依賴項升級會在 merge window 期間批量落地，而新驅動程式及 subsystem 代碼則以小批、分開審核的增量形式加入 — 因此，某個 cycle 的標題式行數通常混合了兩者，17,000 行這個數字最好理解為新增及修改代碼的合計量，而非純粹的新增總數。可以肯定的是方向：每個 cycle 收錄的 Rust 代碼都比上一個為多，而令這些代碼保持最新，本身正成為 merge window 的重要組成部分。</p>
<p>Zerocopy 的更新是單純數字之外最值得注意的部分。目前資料並未說明該內嵌函式庫服務於哪個 subsystem — 網絡、buffer 處理抑或其他 — 因此在作更準確描述前，應先對照 pull request 確認其範圍。可以確定的是，Rust-for-Linux 越來越多地附帶自行維護的內嵌依賴項，這意味著上游 crate 發布與 kernel 端更新必須同步追蹤。這個維護循環，而非任何單一功能，正是近期 merge window 反覆出現的主題。</p>
<p>7.4 的其他內容還包括：一個 <code>cmpxchg</code> 模擬函數的相關工作。這不屬於 Rust 的敘事範疇 — 只是佔據大多數 cycle 的一般架構底層工作。</p>
<p>為何此事 beyond 郵件列表之外仍屬重要？對系統程式員、驅動程式作者及基礎設施團隊而言，kernel 中的 Rust 已不再是實驗性的支線：它是一個按正常 merge cycle 節奏更新、持續維護並不斷擴大的界面。自行攜帶 kernel patch 或 out-of-tree module 的機構，如今有實際動機去跟隨 Rust-for-Linux 的發布節奏。</p>
