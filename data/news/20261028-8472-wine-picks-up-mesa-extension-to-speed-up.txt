Title: Wine Picks Up Mesa Extension to Speed Up 32-bit OpenGL Under WoW64

<h3>Wine Picks Up Mesa Extension to Speed Up 32-bit OpenGL Under WoW64</h3>
<p>Running 32-bit Windows applications and games through Wine on a 64-bit Linux system should get smoother, thanks to a change that removes an extra copy operation from a common OpenGL fast path. Wine has merged support for a new Mesa extension that lets 32-bit clients map buffers without the cross-architecture pointer problems that previously forced additional data copies.</p>
<p>The work targets Wine's WoW64 mode, the mechanism that lets 32-bit Windows binaries run against 64-bit system libraries. That architecture mismatch is useful — it lets a single 64-bit Wine installation host 32-bit applications without a parallel set of 32-bit libraries — but it creates a subtle problem for OpenGL. When a 32-bit client calls <code>glMapBuffer</code> to get a writable pointer into a graphics buffer, that pointer crosses a width boundary that the two sides do not share, leaving no trustworthy way to pass a mapped-buffer address from one side of the stack to the other.</p>
<p>The result was a workaround: rather than sharing the mapped region, Wine's GL layer had to copy buffer contents across the 32/64-bit boundary to keep things correct. Those copies are invisible to the user in isolation, but they add up on workloads that touch buffers frequently — exactly the pattern seen in applications streaming large textures or repeatedly updating geometry.</p>
<p>The fix arrives as <code>MESA_map_buffer_client_pointer</code>, a Mesa-side extension that provides a proper protocol for negotiating a usable client pointer across the boundary. Wine now detects and uses the extension when available, falling back to the old copying behavior when it is not. Because negotiation happens automatically at runtime, users should not need to configure anything — the benefit appears simply by running a recent Wine with a recent Mesa.</p>
<p><a href="https://www.phoronix.com/news/Wine-Mesa-Map-Buffer-Client-Ptr">Phoronix reports</a> that the effort was led by CodeWeavers, the company behind CrossOver. This merge caps off a longer stretch of WoW64 cleanup: instead of papering over the 32/64-bit split with ad-hoc workarounds, Wine and Mesa now speak a shared protocol about how mapped buffers should be handled.</p>
<p>It is worth setting expectations. This is a performance and correctness fix, not a headline-grabbing feature, and the change spans both sides of the stack — the extension lives in Mesa, the wiring lives in Wine — so it benefits the upstream graphics stack rather than any single vendor fork. Practically, users should expect fewer hitches and steadier frame pacing in 32-bit titles that load heavily from disk or stream large assets, rather than dramatic gains in any one benchmark.</p>
<p>For developers and packagers, the more interesting signal is architectural: rough edges left over from the WoW64 transition are being resolved through proper cross-project protocol rather than driver-specific hacks, which should make future 32-bit graphics work less fragile.</p>
<p>The merge is available immediately for those building Wine from source, and is expected to reach downstream projects such as Proton in due course through their usual release cadences.</p>

<h3>Wine 採用 Mesa 擴充 為 WoW64 下 32 位元 OpenGL 加速鋪路</h3>
<p>在 64 位元 Linux 系統上透過 Wine 執行 32 位元 Windows 應用程式及遊戲，日後應會運行得更為暢順，原因是有一項改動移除了 OpenGL 常見快速路徑中的額外複製操作。Wine 已合併對一項全新 Mesa 擴充的支援，讓 32 位元客戶端得以映射 buffer，而毋須面對以往迫使系統進行額外數據複製的跨架構指標問題。</p>
<p>是項工作針對 Wine 的 WoW64 模式——即容許 32 位元 Windows 二進制檔案在 64 位元系統函式庫上執行的機制。該架構不一致固然有用：它令單一的 64 位元 Wine 安裝可同時承載 32 位元應用程式，毋須另設一套並行的 32 位元函式庫；然而，這亦為 OpenGL 帶來一個隱蔽問題。當 32 位元客戶端呼叫 <code>glMapBuffer</code> 以取得圖形 buffer 的可寫入指標時，該指標會跨越雙方並不共用的位元寬度邊界，導致映射 buffer 的地址無法以可信方式由堆疊的一端傳遞至另一端。</p>
<p>結果是產生了一個變通方案：Wine 的 GL 層毋須共享映射區域，反而必須跨越 32/64 位元邊界複製 buffer 內容，以維持運作正確。單獨來看，這些複製操作對用戶並不可見，但在頻繁接觸 buffer 的工作負載下便會累積起來——這正是大量串流大型 texture 或不斷更新幾何資料的應用程式所呈現的模式。</p>
<p>修復方案以 <code>MESA_map_buffer_client_pointer</code> 的形式登場，這是一項 Mesa 端的擴充，為跨越邊界協商可用客戶端指標提供了妥善的協議。Wine 現已能在擴充可用時偵測並加以使用，否則便回退至舊有的複製方式。由於協商在執行期間自動進行，用戶毋須作任何設定——只需執行較新版本的 Wine 及 Mesa，便可獲得相關效益。</p>
<p><a href="https://www.phoronix.com/news/Wine-Mesa-Map-Buffer-Client-Ptr">Phoronix 報道</a>指出，是項工作由 CodeWeavers 主導，該公司為 CrossOver 的背後開發者。此次合併為一連串 WoW64 整理工作畫上句號：Wine 與 Mesa 現已就映射 buffer 的處理方式訂立共用協議，而非以臨時變通方案掩蓋 32/64 位元的分野。</p>
<p>值得調整一下預期。這是效能與正確性的修復，並非引人注目的功能，而且改動牽涉堆疊的兩端——擴充位於 Mesa，相關整合程式位於 Wine——因此受惠的是上游圖形堆疊，而非任何單一廠商的分支版本。實際而言，用戶可望在大量從磁碟載入或串流大型 asset 的 32 位元遊戲中，獲得更少卡頓及更穩定的 frame pacing，而非在任何單一 benchmark 中取得大幅進步。</p>
<p>對開發者及封裝維護者（packager）而言，更具參考價值的訊號在於架構層面：WoW64 過渡遺留的未完善之處，正透過正規的跨項目協議解決，而非依賴驅動程式層面的特定 hack，這應會令日後的 32 位元圖形工作更為穩健。</p>
<p>此次合併即時適用於從原始碼編譯 Wine 的用戶；按預期，相關改動日後亦會循下游項目如 Proton 的慣常發佈節奏，於適當時機納入各項目之中。</p>
