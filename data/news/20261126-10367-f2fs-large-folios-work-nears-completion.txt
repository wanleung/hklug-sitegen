Title: F2FS Large Folios Work Nears Completion, With Android and Embedded Devices in Scope
Content:
<hr />
<p>Hardware and mobile teams that build on Linux-based embedded and Android platforms typically watch F2FS changes closely, and the file system is now approaching one of its more consequential performance updates in recent years. In a recent report, Phoronix says developer Nanzhe Zhao has spent recent months implementing large-folio support for most readable and writable files within F2FS's buffered I/O paths, and that the work may be finished in time to land in the Linux 7.5 kernel.</p>
<p>Large folios allow the kernel to manage file data in bigger, contiguous chunks than the traditional single-page unit. Fewer, larger structures generally mean reduced bookkeeping overhead and better cache behaviour for workloads that read and write file data through the page cache. For a file system used extensively on flash-based mobile and embedded devices, that translates into potentially meaningful everyday performance gains rather than an improvement visible only in synthetic benchmarks.</p>
<p>The scope of Zhao's series is what makes the update notable. Earlier large-folios efforts across the kernel's file systems tended to cover narrower cases; this work targets most readable and writable files across F2FS's buffered paths. That breadth matters because it determines whether real applications see a benefit or whether the improvement is confined to specialised access patterns.</p>
<p>It is also the latest thread in a longer-running, cross-cutting effort to bring folio support to more of the kernel's memory-management and storage stack — a multi-year initiative that has been steadily working through individual file systems. F2FS arrived later than peers such as XFS, ext4, Btrfs and tmpfs, and for good reason: its cluster-oriented on-disk structures, including compression and cluster-mode writes, interact with garbage collection and atomic-write paths in ways that make swapping the page-cache unit size a non-trivial retrofit.</p>
<p>Two caveats are worth noting for planners. First, the benefits described here apply to buffered I/O; workloads dominated by direct I/O or bound by device latency should not expect an obvious change. Second, the Linux 7.5 target reflects the current state of an ongoing patch series — nothing has been merged yet — rather than a guaranteed outcome. Merge-window timing depends on review progress, and the series could slip to a later release. Phoronix's report sets out the current status as of writing.</p>
<p>For teams scoping device and platform roadmaps around upcoming kernel releases, the practical takeaway is that F2FS's long-standing performance gap against other mainstream Linux file systems may finally be narrowing — if the series lands as hoped, Android and embedded deployments running buffered workloads stand to benefit first.</p>
<hr>
<hr />
<p>在 Linux 嵌入式及 Android 平台上進行開發的硬件與流動裝置團隊，向來密切留意 F2FS 的變動，而這個檔案系統即將迎來近年其中一次影響深遠的效能更新。Phoronix 最近一篇報道指出，開發者 Nanzhe Zhao 過去數月一直在為 F2FS 緩衝 I/O 路徑下大部分可讀寫檔案引入 large folio 支援，該工作有機會及時合入 Linux 7.5 內核。</p>
<p>大型 folio 讓內核得以以比傳統單一頁面單位更大的連續區塊來管理檔案數據。一般而言，數量更少、體積更大的結構會令簿記開銷降低，並使透過 page cache 讀寫檔案數據的工作負載獲得更佳的 cache 表現。對於一個在基於閃存的流動及嵌入式裝置上廣泛使用的檔案系統而言，這表示可能帶來實質的日常效能提升，而不只是在合成基準測試中可見的改善。</p>
<p>令這次更新備受矚目的，正是 Zhao 這一系列補丁的覆蓋範圍。此前內核各檔案系統的大型 folio 工作往往只涵蓋較窄的場景；是次工作則針對 F2FS 緩衝路徑下大部分可讀寫檔案。這種廣度至關重要，因為它決定了實際應用能否受益，還是改善僅限於特定的存取模式。</p>
<p>這也是為期多年、橫跨多個子系統的 folio 支援推廣工作中最新的一環——該計劃持續為內核更多記憶體管理及儲存元件引入 folio 支援，並逐個檔案系統逐步推進。F2FS 比起 XFS、ext4、Btrfs 及 tmpfs 等同儕起步較遲，而且事出有因：其以 cluster 為本的磁盤結構，包括壓縮及 cluster 模式寫入，與垃圾回收（garbage collection）及 atomic write 路徑相互交織，令更換 page cache 單位大小並非一項輕而易舉的改動。</p>
<p>規劃者需留意兩點注意事項。第一，此處所述的得益適用於緩衝 I/O；以 direct I/O 為主或受設備延遲限制的工作負載，不應預期有明顯改變。第二，Linux 7.5 的目標反映的是一組仍在進行中的補丁系列的現狀（目前尚未合入任何內容），並非保證的結果。合併窗口（merge window）的時間取決於審核進度，該系列可能延遲至較後的版本。Phoronix 的報道列出了撰稿時的最新狀態。</p>
<p>對於正圍繞即將發佈的內核版本來制訂設備及平台路線圖的團隊，實際的啟示是：F2FS 長期以來相對其他主流 Linux 檔案系統的效能差距，可能終於開始收窄——倘若該系列能如預期合入，首先受惠的將會是執行緩衝工作負載的 Android 及嵌入式部署。</p>
