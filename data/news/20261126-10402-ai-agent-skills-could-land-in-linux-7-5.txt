<h3>AI agent skills could land in Linux 7.5: in-tree docs to guide agents through core processes</h3>
<p>According to Phoronix, the Linux 7.5 merge window — due to open in late December — is expected to receive an "AI agent skills" submission: documentation maintained alongside the kernel source tree, instructing AI agents on how to take part in core development processes. In other words, this is a planned submission still awaiting review on LKML, not merged code.</p>
<h4>What happened</h4>
<p>The proposal calls for adding a document inside the kernel source tree that explains how various core development processes should be understood and carried out by AI agents. When developers use AI assistants to help draft or organise patches, the guidance the agent receives comes from the project itself rather than scattered external prompts.</p>
<p>Before the merge window formally opens, proposals like this are still publicly debated on LKML; whether it makes it into 7.5 will depend on maintainer consensus and the outcome of that review.</p>
<h4>Why in-tree matters</h4>
<p>The most notable aspect of this proposal is less the "AI" than the governance model. Placing agent guidance inside the source tree means it can be amended, challenged and reviewed like any other file, leaving a complete trail through the project's existing version control and review workflow; by contrast, externally maintained prompt libraries or knowledge bases can silently go stale as the project evolves, without anyone noticing.</p>
<p>For the kernel community, this arrangement upholds the long-standing principle that anything affecting the development process should be visible and traceable. If one of the most process-driven, conservative large open-source projects establishes an in-tree format for agent instructions first, others may follow, setting an industry reference point.</p>
<h4>Impact on contributor workflows</h4>
<p>For developers who submit patches day to day, the short-term impact is limited — it will not change how the kernel is built or its interfaces. The real change sits one layer down: when an AI assistant understands and organises patches according to the project's own rules, it should theoretically reduce the number of rejections caused by formatting or convention mismatches, letting review discussions focus more on the code itself.</p>
<h4>Hong Kong perspective: local enterprise Linux/cloud teams</h4>
<p>For Hong Kong's enterprise Linux and cloud infrastructure teams, the reference value of this proposal lies in its governance logic: placing rules somewhere versionable and auditable, and letting them evolve through normal processes. That thinking is instructive for any organisation that houses AI assistant guidance in internal knowledge bases; how local teams actually adopt it is a matter for each team to decide, and this article makes no assumptions. Practitioners who use AI coding assistants daily should also note: who maintains the instructions, and how they are updated as workflows change, remains an open question worth watching.</p>
<h4>Open questions still unresolved</h4>
<p>Until the proposal is formally submitted and reviewed on LKML, several questions remain unsettled: who will maintain these skills long-term, how they will be updated as workflows evolve, and whether a single set of instructions might unintentionally favour the conventions of certain AI vendors.</p>

<h3>AI agent skills 可能登陸 Linux 7.5：in-tree 文件指導代理參與核心流程</h3>
<p>據 Phoronix 報道，即將於十二月下旬展開的 Linux 7.5 合併視窗，預計會收到一項「AI agent skills」提交：在核心原始碼樹內維護文件，指示 AI 代理如何參與核心開發流程。換言之，這是計劃提交、尚待 LKML 審閱的變更，並非已合併的程式碼。</p>
<h4>發生了什麼</h4>
<p>提案的具體做法，是在核心原始碼樹內加入文件，說明各項核心開發流程應如何被 AI 代理理解和執行。當開發者使用 AI 助手協助撰寫或整理補丁時，代理取得的指引來自專案本身，而非零散的外部提示。</p>
<p>在正式進入合併視窗之前，這類提議仍會先在 LKML 公開討論；最終能否納入 7.5，要視乎維護者共識與審閱結果。</p>
<h4>為何 in-tree 是關鍵</h4>
<p>這項提議最值得注意的地方，與其說是「AI」，不如說是治理方式。把代理指引放進原始碼樹，意味著它與其他任何檔案一樣，可以被修改、被質疑、被審核，並透過核心專案既有的版本控制與審查流程保留完整紀錄；相比之下，由外部維護的提示詞庫或知識庫，容易在專案演進之後悄然過時，卻無人察覺。</p>
<p>對核心社群而言，這種安排維持了「所有影響開發流程的東西都應該可見、可追查」的一貫原則。若最講究流程的大型開源專案都先為代理指令訂立一個 in-tree 格式，其他大型專案可能會跟隨，成為業界參考的先例。</p>
<h4>對貢獻者工作流的影響</h4>
<p>對日常提交補丁的開發者來說，短期影響有限——它不會改變編譯方式或介面。真正的變化在於間接層：當 AI 助手按照專案自己的規則去理解和整理補丁，理論上可以減少因格式、慣例不符而被打回的次數，讓審查討論更集中在程式碼本身。</p>
<h4>香港角度：本地企業 Linux／雲端團隊</h4>
<p>對香港的企業 Linux 與雲端基建團隊而言，這項提議的參考價值集中在治理邏輯：把規則放在可版本化、可審核的位置，交由正常流程演進。這一思路對任何以內部知識庫承載 AI 助手指引的組織都具啟發性；至於本地團隊實際如何採用，屬各團隊自行判斷，本文不作推斷。日常使用 AI 編碼助理的從業者亦宜留意：指令內容由誰維護、如何隨工作流更新，仍是值得持續觀察的一環。</p>
<h4>仍未解決的問題</h4>
<p>在提案正式提交並經 LKML 審閱前，幾個問題尚無定論：這些 skills 由誰長期維護、如何隨工作流演變而更新，以及一套統一的指令會否在無意間偏向某些 AI 供應商的慣例。</p>
