Title: Kernel Builds to Speed Up as Linux 7.4 Drops LLVM Profi from AutoFDO Pipelines
Content:
<p>Kernel and CI builders are set to see meaningful changes to their AutoFDO-assisted builds: a change merged into the Linux 7.4 kernel disables LLVM's Profi flow-based profile inference algorithm for AutoFDO workflows, and it is also slated for back-porting to stable kernel branches — meaning LTS and distribution builders will be affected before 7.4 itself ships. Phoronix reported the merge earlier this week.</p>
<p>The motivation is twofold. According to Phoronix, Profi was associated with pathological compile times in kernel builds, but also with runtime regressions: in certain configurations, binaries produced with the profile inference pass enabled were slower than those built without it. That second detail is the more notable one. AutoFDO — which feeds real profiling data back into the compiler to guide optimization — is normally expected to trade build complexity for faster code. Here, the analysis layer was undermining the very outcome it exists to serve, making the disable a rare case where an optimization yields a build-time win with no runtime cost attached. The report keeps the performance claim directional rather than attaching specific regression percentages, and it does not spell out whether the slowdown was measured across all AutoFDO configurations or a narrower subset.</p>
<p>Importantly, Profi is disabled by default, not removed from the toolchain. Builders and developers who have measured a genuine benefit from the pass in their own workloads can still opt back in; what changes is the default posture for AutoFDO-enabled kernel builds, where the evidence of harm outweighs the presumed gain.</p>
<p>For maintainers of long-term and stable kernels, the back-port is the operative part of the story. Because the change travels through stable updates rather than waiting for the 7.4 merge window to reach production systems, organizations running LTS kernels through a CI pipeline may find their build timings and binary performance characteristics shifting on the next routine update. The report does not name which stable branches will receive the change first, or where each sits in the queue, so teams should confirm the status against their own distribution's update feed. Teams with benchmarking in place for kernel build performance and post-build runtime should treat the next stable refresh as a checkpoint rather than a routine roll.</p>
<p>The incident also illustrates a broader lesson for anyone tuning compiler-driven optimization at scale. Profi infers profile information from flow analysis rather than from direct measurement, and at kernel scale — with its enormous, heavily branched translation units — inferred data can diverge from what the hardware actually does. More compiler analysis does not automatically mean better results, and optimization passes that look beneficial on smaller codebases warrant continuous validation as they are applied to larger ones. The kernel's AutoFDO experience suggests profile inference passes are a good candidate for exactly that kind of periodic re-checking.</p>
<p>AutoFDO itself remains a supported and widely used technique for kernel builds; the change targets one specific inference algorithm within the pipeline rather than the feedback-directed optimization approach as a whole. Builders evaluating their own configurations should confirm the precise scope of affected setups — AutoFDO-only, or a broader set of ThinLTO- and CFI-assisted builds — before drawing conclusions about their own build environments.</p>
<p>For teams maintaining kernel-based infrastructure anywhere — Hong Kong included — the practical takeaway is straightforward: expect stable-branch updates to arrive with changed build behavior, and verify that CI build-time and runtime benchmarks reflect the new default before the change reaches production images.</p>
<hr>
<p>核心編譯及持續整合（CI）建置人員即將迎來 AutoFDO 輔助建置流程的重要變動：一項已合併至 Linux 7.4 核心的改動，會在 AutoFDO 工作流程中停用 LLVM 的 Profi 流程分析（flow-based）profile 推斷演算法，同時該改動亦計劃回移（back-port）至穩定版本核心分支——這意味著 LTS 及各發行版的建置人員在 7.4 正式發布前便會受到影響。Phoronix 早於本星期初報道了此次合併。</p>
<p>改動的動機有二。據 Phoronix 報道，Profi 曾與核心建置中極端漫長的編譯時間有關，亦同時引致執行效能倒退：在某些配置下，啟用 profile 推斷 pass 所產生的二進位檔案，執行速度反而比未啟用時更慢。後者尤為值得注意。AutoFDO 的運作原理是將實際剖析數據回饋至編譯器以引導優化，一般預期是以增加建置複雜度換取更快的程式碼。然而在此情況下，分析層反而削弱了它本應達成的成效，使得今次停用成為罕見案例——某項優化帶來建置時間上的收益，卻沒有附帶執行效能代價。報道對效能說法只作方向性描述，並未列出具體的倒退百分比，亦沒有明言速度變慢是在所有 AutoFDO 配置下量度，還是僅限於較狹窄的配置子集。</p>
<p>值得注意的是，Profi 只是預設停用，並未從工具鏈中移除。建置人員及開發者如曾在自身工作負載中量度到該 pass 的確切效益，仍可自行重新啟用；改變的是啟用 AutoFDO 的核心建置之預設取向——有害的證據已蓋過預期收益。</p>
<p>對長期及穩定版本核心的維護者而言，回移才是整件事的關鍵所在。由於改動是透過穩定版本更新推送，而非等待 7.4 的合併視窗才觸及生產系統，透過 CI pipeline 運行 LTS 核心的機構，可能在下一次例行更新時便發現建置時間及二進位檔案執行特性出現變化。報道並未點名哪些穩定分支會最先接收改動，亦沒有說明各分支在佇列中的位置，因此團隊應向所用發行版的更新源核實改動狀態。已建立核心建置效能及建置後執行基準測試的團隊，應將下一次穩定版本更新視為一個檢查點，而非例行滾動更新。</p>
<p>今次事件亦為所有在大規模環境下調校編譯器驅動優化的人士帶來一個更廣泛的啟示。Profi 是從流程分析而非直接量度推斷 profile 資訊，而在核心規模下——面對龐大且分支眾多的翻譯單元——推斷所得的數據可能偏離硬件的實際行為。更多編譯器分析不等於自動帶來更好結果，在較小程式碼庫中看似有益的優化 pass，當應用於更大規模時需要持續驗證。核心的 AutoFDO 經驗正說明，profile 推斷 pass 恰恰是需要此類定期複檢的對象。</p>
<p>AutoFDO 本身仍然是核心建置中受支持且廣泛應用的技術；今次改動針對的是流程內其中一個特定的推斷演算法，而非整套反饋導向優化方法。建置人員評估自身配置前，應先確認受影響配置的確切範圍——是僅限 AutoFDO，還是包括更廣泛的 ThinLTO 及 CFI 輔助建置——然後才就自身的建置環境作出結論。</p>
<p>對任何地方（包括香港）維護核心基礎設施的團隊而言，實際的要點很直接：預期穩定分支更新會伴隨建置行為的改變，並在改動抵達生產映像之前，核實 CI 的建置時間及執行基準測試已反映新的預設設定。</p>
