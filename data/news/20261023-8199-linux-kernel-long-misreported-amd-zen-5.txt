Title: Linux Kernel Long Misreported AMD Zen 5 TLB Figures — Linux 7.4 Finally Corrects Them
Content:
<p>A long-running discrepancy in how the Linux kernel reports translation lookaside buffer (TLB) sizes on AMD Zen 5 processors has been resolved, with Phoronix reporting that the correction has merged for the Linux 7.4 kernel — closing out work first flagged in September and putting a quietly consequential accuracy bug to rest, rather than a crash or a security hole.</p>
<p>The problem is one of measurement, not breakage. Affected AMD CPUs advertise TLB geometry to the kernel that is smaller than what the silicon actually provides. Kernel heuristics lean on that figure when deciding how aggressively to manage page mappings and adjacent structures, so an understated value pushes the kernel to tune against a more cramped cache than really exists. Nothing fails; workloads simply leave performance unclaimed. That "quiet, not breaking" quality is why the issue stayed below the radar of everyone outside performance-tuning circles for months.</p>
<p>The more interesting part of the story is how the fix is built. Rather than hard-coding corrected constants against individual Zen 5 part numbers, Phoronix reports the patch derives TLB geometry from the kernel's existing CPU identification logic — a deliberate choice, since maintainers have long favoured detection-based reasoning over per-SKU tables that rot the moment new steppings and microarchitectures ship. The upshot is that the correction generalises across "Zen 5 and newer" AMD parts: any future microarchitecture that walks the same identification path inherits the corrected reporting automatically, with no follow-up patch needed. It is a clear step up from the historical pattern of chasing one-off errata model family by model family.</p>
<p>The change is queued for Linux 7.4. As with any merge-window work, operators should treat distribution release notes and kernel.org changelogs as the authoritative source when pinning an exact release for an upgrade — standard hygiene for planning cycles, since delivery timing varies by distro rather than by the merge itself.</p>
<p>The practical effect is fleet-level and workload-dependent. AMD EPYC servers and Ryzen workstations are the systems in scope, and the visible benefit concentrates in memory-bound scenarios: databases, virtualisation hosts, in-memory analytics, and other working-set-heavy services where TLB pressure is actually measurable. Where TLB misses are already a monitored metric, the corrected reporting should show up as a modest tuning improvement; elsewhere it will be indistinguishable from run-to-run noise. This is not a headline speedup, and anyone benchmarking before and after should guard against over-reading small deltas. Distribution cadence decides who gets it first — fast-moving, promptly rebased releases typically carry merged mainline changes well ahead of long-term-support tracks, so teams pinned to an LTS release may wait a cycle or two.</p>
<p>For Hong Kong data-centre and workstation teams running AMD hardware, the wider lesson is about benchmarking hygiene as much as kernel versioning: when the operating system misreports hardware geometry, any performance model built on that reporting inherits the error, and tuning conclusions drawn from it can be quietly wrong.</p>
<p>For teams scheduling kernel upgrades over the coming months, the sensible course is to log this as a pending tuning improvement on AMD platforms, confirm the shipping release against kernel.org and distribution notes at upgrade time, and re-run memory-bound benchmarks once corrected reporting is in place — rather than expecting an out-of-the-box speed gain.</p>
<hr>
<p>Linux 核心在 AMD Zen 5 處理器上回報轉譯後備緩衝區（translation lookaside buffer，TLB）容量時長期存在數據差異，如今終於解決。Phoronix 報導，相關修正已合併至 Linux 7.4 核心 — 為這項早在九月已標記的工作劃上句號，解決的是一個低調但影響顯著的準確性問題，而非崩潰或保安漏洞。</p>
<p>問題在於量度，而非故障。受影響的 AMD CPU 向核心通報的 TLB 結構參數比晶片實際提供的為少。核心的 heuristic 判斷在決定如何積極管理頁面映射及相鄰結構時，會依賴該數據，因此低估的數值會令核心針對一個實際上較為狹窄的快取來作調校。系統不會出錯；工作負載只是未能發揮應有性能。正是因為這種「低調、不出錯」的特性，問題在性能調校圈子以外沉寂了數月。</p>
<p>此項修復的設計更為值得注意。據 Phoronix 報導，補丁並非針對個別 Zen 5 型號硬編碼修正後的常數，而是從核心現有的 CPU 識別邏輯推導出 TLB 結構參數 — 這是有意為之，因為維護者向來傾向以偵測為本的判斷，取代一經新 stepping 及微架構推出便會失效的逐型號列表。其結果是，修正可適用於「Zen 5 及更新」的 AMD 處理器：任何日後沿用相同識別路徑的微架構，都會自動繼承修正後的回報數據，毋須另出補丁。相比以往逐個型號系列追查一次性勘誤的舊模式，這明顯是進步。</p>
<p>該變更已排入 Linux 7.4。一如任何 merge window 的工作，營運者在鎖定升級至某個確切版本時，應以發行版發行說明及 kernel.org 變更日誌為權威依據 — 這是規劃升級周期的標準做法，因為實際推出時間取決於發行版，而非合併本身。</p>
<p>實際效果以機群為單位，並取決於工作負載。範圍涵蓋 AMD EPYC 伺服器及 Ryzen 工作站，而可見的效益集中在受記憶體限制的情景：數據庫、virtualisation 主機、記憶體內分析，以及其他 working set 需求沉重、TLB 壓力確實可量度的服務。在 TLB miss 本身已是監控指標的環境，修正後的數據應會反映為適度的調校改進；其他情況下則與運行間的隨機噪音無異。這並非標題式的性能提升，進行前後對比基準測試者應避免過度解讀微小差異。哪個群組先獲得更新，取決於發行版節奏 — 推出迅速、及時 rebase 的版本通常遠早於長期支援（LTS）軌道採用已合併的主線變更，因此鎖定 LTS 版本的團隊可能要等一至兩個周期。</p>
<p>對香港數據中心及工作站團隊而言，若正在運行 AMD 硬件，更廣泛的啟示不僅涉及核心版本管理，亦關乎基準測試的嚴謹性：當操作系統誤報硬件結構參數時，任何建基於該回報的性能模型都會繼承錯誤，由此得出的調校結論可能在不經意間是錯的。</p>
<p>對於未來數月安排核心升級的團隊，合理做法是將此項記錄為 AMD 平台上待落實的調校改進，升級時按 kernel.org 及發行版說明確認實際推出的版本，並在修正後的回報數據生效後重新進行受記憶體限制的基準測試 — 而不是期待開箱即用的速度提升。</p>
