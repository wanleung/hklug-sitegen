Title: Drupal Scrambles to Close Critical RCE Hole as Public Exploits Loom
Content:
<p>The Drupal Security Team has shipped a fix for a critical remote code execution vulnerability that would let an attacker take complete control of a vulnerable site — and is warning that working exploits could appear in public shortly after the disclosure goes live.</p>
<p>Administrators who have not yet assessed their exposure should start there: consult the Drupal Security Team's advisory directly for the affected version range and advisory identifiers, and treat the update as an immediate priority rather than something to fold into the next routine maintenance window.</p>
<h4>Why the window is measured in days</h4>
<p>The uncomfortable detail in this disclosure is its timing. Drupal publishes its advisory and the corresponding code diffs at the same moment, which means the patch itself effectively documents the bug for anyone willing to read it. Reverse-engineering a fix into a working exploit is a routine task for a motivated attacker, so the period between disclosure and weaponisation is realistically days rather than weeks.</p>
<p>Drupal's own history illustrates the risk. In 2018, the Drupalgeddon flaws (CVE-2018-7600 and its successor) were followed by mass exploitation within hours of disclosure, with automated scanners sweeping the internet for unpatched installations. That precedent is why the security team is warning about rapid exploit availability now, and why administrators should not assume they have the luxury of scheduling the update into the next maintenance window.</p>
<h4>What the security team is asking administrators to do</h4>
<ol>
<li><strong>Update first.</strong> Apply the patched Drupal core release to every affected site immediately. Where the release notes flag end-of-life branches, remember that no backport is coming — those installations need a supported version to be secure at all.</li>
<li><strong>Compensate while you queue the change.</strong> Where an immediate upgrade is impossible, restrict administrative interfaces behind access controls or VPNs and disable any unnecessary functionality that widens the attack surface.</li>
<li><strong>Audit contributed modules.</strong> Core's fix only covers core. Third-party modules that interact with the patched subsystem should be checked for their own updates or disabled if unmaintained.</li>
<li><strong>Assume the window may already have closed.</strong> Review access and error logs for anomalous administrative activity, rotate privileged credentials, and confirm that backups are intact and restorable before an incident forces the question.</li>
</ol>
<h4>Why this matters beyond the patch</h4>
<p>Drupal underpins a substantial number of government, education and enterprise publishing platforms worldwide. For IT teams in Hong Kong and elsewhere, the story is a familiar one: in open-source ecosystems where disclosure and fix ship together, patch latency — not patch availability — is the real exposure metric, and any organisation without a tested, fast path to deploying upstream releases is already behind an attacker working from the same diffs.</p>

<hr>
<p>Drupal 安全團隊已發布修補程式，處理一個可讓攻擊者完全控制受害網站的重大遠端程式碼執行漏洞，同時警告公開的漏洞利用程式可能在漏洞披露後不久便會出現。</p>
<p>尚未評估自身風險的管理員應先做一件事：直接查閱 Drupal 安全團隊的公告，確認受影響的版本範圍及公告編號，並將是次更新列為即時優先事項，而不是排入下一個例行維護時段處理。</p>
<h4>為何窗口以天計算</h4>
<p>是次披露中最令人不安的，是它的時機。Drupal 會在同一時間發布公告與對應的程式碼差異（diff），這意味著修補程式本身等同為任何願意閱讀的人說明了漏洞的原理。對有動機的攻擊者而言，從修補程式反向推導出可用的漏洞利用程式是例行功課，因此由披露到武器化的時間，實際上以天計，而非以星期計。</p>
<p>Drupal 的歷史正好說明風險。2018 年的 Drupalgeddon 漏洞（CVE-2018-7600 及其後續漏洞）在披露後數小時內即遭大規模利用，自動掃描器在互聯網上搜尋未安裝修補程式的系統。這正是安全團隊如今警告漏洞利用程式可能迅速出現的原因，也說明管理員不應假設自己還有餘裕，把更新排進下一個維護時段。</p>
<h4>安全團隊要求管理員採取的行動</h4>
<ol>
<li><strong>先更新。</strong>立即為所有受影響網站套用已修補的 Drupal core 版本。若發行說明標示某些分支已停止維護，請記住不會再有 backport——這些安裝必須遷移至受支援的版本，才能獲得基本安全保障。</li>
<li><strong>排隊期間先做緩解。</strong>若無法即時升級，應將管理介面限制於存取控制或 VPN 之後，並停用任何會擴大攻擊面的非必要功能。</li>
<li><strong>檢查附加模組。</strong>core 的修補只涵蓋 core。與受修補子系統互動的第三方模組，應一併檢查是否有更新，或在無人維護時停用。</li>
<li><strong>假設窗口可能已關閉。</strong>檢查存取及錯誤日誌中有無異常的管理員活動，輪換高權限憑證，並確認備份完整、可還原——不要等到事故發生才被迫面對問題。</li>
</ol>
<h4>為何這不只是補上一個修補的問題</h4>
<p>Drupal 支撐著全球大量政府、教育及企業的內容發布平台。對香港及其他地區的 IT 團隊而言，故事並不陌生：在披露與修補同時發布的開源生態系中，真正的風險指標是修補延遲，而非修補是否已經存在——任何沒有經過測試、可快速部署上游版本流程的機構，早已落後於正在閱讀同一份程式碼差異的攻擊者。</p>
