Title: GitLab 修補 CVSS 10.0 最高危漏洞：特定條件下未經驗證用戶可在伺服器執行任意代碼
Content:
<p>GitLab 已發布安全修補，處理一個評分達 CVSS 10.0 滿分的最高嚴重性漏洞：影響 Community Edition（CE）與 Enterprise Edition（EE）自架部署，在特定條件下可讓<strong>未經驗證用戶</strong>透過在 CI/CD 中提交特別構造的正規表示式（regular expression），在 GitLab 伺服器上執行任意代碼。管理員應視此為本週最高優先事項——未驗證即可觸發的伺服器端代碼執行，等同於把整個實例的控制權交到匿名訪客手上。</p>
<h4>影響範圍：以官方 advisory 為唯一依據</h4>
<p>截至發稿時，本刊尚未取得 GitLab 官方安全發布說明的完整版本區間與 CVE 編號，因此本文不列出任何版本數字——對一份修補 advisory 來說，錯誤的版本範圍比空白更具危險性。管理員請直接查閱 <a href="https://about.gitlab.com/releases/">GitLab 官方安全發布說明</a>，確認手上的 CE/EE 版本是否落入受影響範圍，以及應升級至哪個修復版本。官方公告發布後，本文將補上完整版本對照表。</p>
<p>需要特別留意的是，GitLab 公告使用了「在特定條件下」這一限定詞，但並未說明條件的具體內容（例如是否需要特定 pipeline 權限或觸發路徑）。攻擊面的實際寬度取決於各實例的部署與設定方式，不應一概而論為「所有自架實例均直接暴露」，但也不應樂觀假設自己的設定不在範圍內——正確做法是以官方版本區間為準進行資產比對。</p>
<h4>利用狀態</h4>
<p>來源資料並未提及是否已有公開的實戰利用或概念驗證（PoC）流出。在證據明朗之前，本刊的判斷是：一個 CVSS 10.0、未驗證即可觸發的 RCE，應按「可能已被利用」的標準處理，即刻排查並修補，而不是等待確證。</p>
<h4>為什麼對自架 GitLab 團隊特別重要</h4>
<p>本漏洞直接影響的是自架 CE/EE 部署；使用 GitLab.com SaaS 的團隊不在本次 advisory 的針對範圍內。對自架用戶而言，一旦被利用，攻擊者取得的不僅是程式碼庫——CI/CD Runner 上的憑證、部署金鑰與生產環境存取權限，很可能一併落入對方手中，等於從一次 pipeline 提交升級為整條供應鏈的失守。</p>
<h4>修補與自查清單（建議按序執行）</h4>
<ol>
<li><strong>識別資產</strong>：列出所有自架 GitLab CE/EE 實例、版本號與對外暴露情況；比對官方公告的受影響版本區間。</li>
<li><strong>優先修補</strong>：將官方公告指定的修復版本列入本週變更窗口，先行處理對外可達、且啟用 CI/CD 的實例。</li>
<li><strong>過渡期緩解</strong>（僅為權宜之計，不能取代修補）：</li>
<li>收緊網絡層存取，限制 GitLab Web 與 API 端點的來源 IP。</li>
<li>暫停或審查來源不明的 CI/CD pipeline 觸發權限。</li>
<li><strong>日誌審計</strong>：檢查近期 CI/CD job 建立與正規表示式相關的異常活動、陌生 pipeline 來源及服務帳戶的非常規行為。</li>
<li><strong>憑證輪換</strong>：一旦發現可疑跡象，立即輪換 CI/CD 變數中的 token、部署金鑰與 GitLab 互通的第三方整合憑證。</li>
<li><strong>後續跟進</strong>：追蹤 GitLab 完整公告以釐清攻擊的確切前置條件（例如是否需特定 pipeline 權限），並留意本地 CERT 是否另行發布提示。</li>
</ol>
<p>漏洞公告詳情、CVE 編號與完整版本清單，請參見 <a href="https://about.gitlab.com/releases/">GitLab 官方安全發布說明</a> 及 <a href="https://thehackernews.com/2026/10/gitlab-patches-cvss-100-flaw-that-could.html">The Hacker News 原始報導</a>。本刊取得官方完整版本區間後將更新本文。</p>

<hr />
<p>GitLab has released patches for a maximum-severity flaw scoring a perfect CVSS 10.0, affecting both Community Edition (CE) and Enterprise Edition (EE) self-managed deployments. Under certain conditions, an unauthenticated user could execute arbitrary code on the GitLab server by submitting a specially crafted regular expression through a CI/CD workflow. Administrators should treat this as the week's top priority — unauthenticated server-side code execution is functionally equivalent to handing an anonymous visitor the keys to the entire instance.</p>
<h4>Scope: Anchor Everything to the Official Advisory</h4>
<p>At the time of publication, we have not yet been able to retrieve GitLab's official security release notes with complete affected and fixed version ranges, or the CVE identifier. For that reason, this article does not name specific version numbers — in a patch advisory, an incorrect version range is more dangerous than a blank one. Administrators should go directly to <a href="https://about.gitlab.com/releases/">GitLab's official security releases page</a> to confirm whether their CE/EE version falls within the affected range and which fixed release to upgrade to. We will update this article with a full version table once the official advisory is published.</p>
<p>One detail warrants particular attention: GitLab's notice uses the qualifier "under certain conditions," but does not spell out what those conditions are — whether, for instance, a specific pipeline permission or trigger path is required. The actual breadth of the attack surface depends on how each instance is deployed and configured. It would be wrong to flatten this into "all self-managed instances are exposed," but it would also be wrong to assume cheerfully that your configuration falls outside the range. The correct move is asset-by-asset comparison against the official version ranges.</p>
<h4>Exploitation Status</h4>
<p>The source material does not mention whether public in-the-wild exploitation or a proof-of-concept (PoC) has surfaced. Until the evidence is clearer, our editorial judgment is this: a CVSS 10.0, unauthenticated RCE should be handled as though it may already have been exploited — patch and audit now, rather than waiting for confirmation.</p>
<h4>Why This Matters for Self-Managed GitLab Teams</h4>
<p>This vulnerability directly affects self-managed CE/EE deployments; teams running GitLab.com SaaS are not the target of this advisory. For those running their own instances, the damage if exploited extends well beyond the source repository — credentials on CI/CD Runners, deployment keys, and production environment access are all likely to fall with it, turning a single pipeline submission into a supply-chain breach.</p>
<h4>Patch and Self-Check Checklist (Execute in Order)</h4>
<ol>
<li><strong>Identify assets</strong>: List every self-managed GitLab CE/EE instance, its version, and its external exposure; compare against the affected version ranges in the official advisory.</li>
<li><strong>Patch first</strong>: Add the official fixed versions to this week's change window, prioritizing instances that are externally reachable and have CI/CD enabled.</li>
<li><strong>Interim mitigation</strong> (a stopgap only — not a substitute for patching):</li>
<li>Tighten network-layer access, restricting source IPs allowed to reach GitLab's web and API endpoints.</li>
<li>Pause or audit CI/CD pipeline trigger permissions from unfamiliar sources.</li>
<li><strong>Log audit</strong>: Review recent CI/CD job activity for anomalous regular expressions, unfamiliar pipeline origins, and service-account behavior outside normal patterns.</li>
<li><strong>Credential rotation</strong>: At the first sign of suspicious activity, rotate tokens in CI/CD variables, deployment keys, and any third-party integrations that authenticate against GitLab.</li>
<li><strong>Follow-up</strong>: Track GitLab's full advisory to pin down the exact preconditions of exploitation (for example, whether a specific pipeline permission is required), and watch for advisories from your local CERT.</li>
</ol>
<p>For the vulnerability details, CVE identifier, and complete version list, see <a href="https://about.gitlab.com/releases/">GitLab's official security releases</a> and <a href="https://thehackernews.com/2026/10/gitlab-patches-cvss-100-flaw-that-could.html">The Hacker News' original report</a>. We will update this article once we have GitLab's full affected-version ranges.</p>
